## 最新最小文本的执行内容

1. 恢复本机 Docker、开发 PostgreSQL/Redis、Go/Air、Vite 和原生 Bun worker。保留既有数据库及代理配置。
2. 按分组名称读取 21 个实际账号、各自代理绑定和模型映射，不创建测试账号或临时模型别名。
3. 测试开始有 20 条历史限流记录，但未来冷却数为 0；这些历史记录均已过期。逐实例调用前清除其旧限流标记，共清理 20 次，没有重置总/日/周 quota usage。
4. 对每个账号固定调用一次 `POST /api/v1/admin/accounts/{id}/test`，单独读取完整后台 SSE。该 Bun 分支不进入 adaptive 多协议测试，不重试或切换账号，也不安排消费网关的自动额度复验。
5. 每条代理另做一次 HTTPS 出口探测；21/21 成功且出口符合环境参考表。出口探测不属于模型推理请求。

管理员诊断请求体：

```json
{
  "model_id": "mimo-v2.6-flash-free",
  "prompt": "What is 2 + 3? Reply with only the number 5."
}
```

Go 构造的调用方 Chat Completions 请求只有 `model`、一条 user message 和 `stream:true`，不携带 Agent system prompt、会话历史或调用方工具。worker 仍按现有 OpenCode 兼容契约加上固定 system 与 `read` 占位工具，设置 `tool_choice:none`、`temperature:0` 和 usage streaming；因此“最小文本”不表示上游最终 JSON 完全没有兼容工具字段。

成功判定要求后台 SSE 无 error、模型正确、唯一成功完成事件，并精确回答 `5`。后台在此之前还校验真实上游 HTTP 200、完整 SSE、合法 usage、`billing_source=free` 和流结束。**管理员接口自身的 HTTP 200 不等于模型成功**，失败也可能通过 SSE error 返回。

本轮日志确认共 21 个测试 HTTP 请求，每账号一次；18 个失败逐条关联到对应 worker 请求，均为 `429 FreeUsageLimitError`。没有后台自动文本探针。21 个账号测试前后的配置指纹一致，代理绑定没有改变；失败后的新冷却由服务正常保留。

## 两个 harness 的真实调用内容

两个客户端均使用本机已有构建，配置、workspace、session、日志和临时目录放在本项目 `.cache/mimo-harness-20261101` 下，保留用户原有 OpenClaw 默认配置。

- **OpenClaw**：普通 `agent --local --agent main`，显式模型 `sub2api-mimo/mimo-v2.6-flash-free`，`thinking=off`、`tools.profile=coding`，没有 lean 模式或工具白名单裁剪。实际请求携带 **39 个工具**，115,570 字节，使用 `max_tokens:4096`。
- **DeepSeek Harness**：已有 `apps/cli/lib/bin.js`，使用 `--profile headless --patch <项目内配置> --json --permission-mode read-only --approval-policy never`，选择 OpenAI completions provider，关闭额外标题模型调用。实际请求携带 **22 个工具**，22,582 字节，使用 `max_completion_tokens:4096`，并带 `store:false`。

每个客户端、每个实例使用新会话，提示词为：

```text
What is 2 + 3? Reply with only the number 5. Do not use any tools.
```

这是保留完整工具目录的单轮 Agent 文本调用，未要求实际执行工具。两个客户端 provider 均配置零自动重试；OpenClaw 还在隔离 Agent settings 中设置 `retry.provider.maxRetries:0`、清空 fallbacks。单次 provider 超时 45 秒，OpenClaw Agent 截止 70 秒，外层进程上限 90 秒。诊断层每个文本案例最多转发一次请求；报告不单独统计被本地预算拦截的客户端尝试。

为了让普通 Mimo 消费 Key 严格命中指定实例，临时为每个账号添加唯一模型别名，并将这些别名加入 group31 白名单。只监听回环地址的诊断转发层把客户端模型改为对应别名；网关通过该账号映射还原真实 Mimo，沿正常鉴权、规范化、代理与 worker 路径派发，响应模型名再还原为客户端配置的 Mimo。没有添加会提前还原别名的渠道映射。

日志核验 42 次主请求全部命中指定账号，每个账号分别承接两个 harness 各一次，串号为 0。服务尝试故障转移时，其余账号不支持该唯一别名，因此没有跨实例的第二次实际派发。

## 历史失败、补测和调用计数

- 两个客户端均成功加载配置、准备工具并发出真实请求，全部以失败结果退出；没有成功回答，也没有进程超时。
- 41 个主请求得到真实上游 `429 FreeUsageLimitError`。这证明当时上游拒绝请求，但不足以单独确定免费额度计数、出口限制或其他准入条件。

## 结果解释与恢复核验

最新证据只能确认 **2026-11-02 08:35～08:36 的最小文本在实例15、16、17上成功**。它与前一日晚间 harness 和后台探针都失败的结果发生在不同时间，不能据此把差异单独归因于工具数量、提示词大小或某个客户端。

清理本地冷却仅撤销本地调度标记，不会重置上游免费额度或改变上游准入策略。其余18个实例在清理旧标记后仍收到上游429，表明本轮失败并非旧本地冷却拦截；具体上游拒绝条件仍未确定。

历史 harness 批次结束后，21 个账号的完整 credentials、代理绑定以及 group31 原始白名单均已逐项核验恢复，临时别名全部删除，恢复错误数为0。恢复的是临时路由配置，业务冷却保留服务判断；当时恢复核验快照有20个账号记录冷却。最新最小文本批次没有再修改模型映射或白名单。

测试工作区基于提交 `4ca561fd3`，并包含测试开始前已有的 `store` 布尔字段兼容改动及其测试，位于 `backend/internal/service/opencode_free_bun_request.go` 和对应测试文件。本轮没有编辑或提交这两份源码；这里记录的是当时开发运行时，不能当作干净提交版本的发布验收。
